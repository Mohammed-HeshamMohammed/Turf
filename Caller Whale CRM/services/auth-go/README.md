# Auth (Go)

The Go rebuild of the authentication service. **Not live yet**: the Rust service in `../auth` is still the one that signs people in, until this one has every route and passes the same tests. Plan, decisions and phases: [docs/plans/go-auth.md](../../docs/plans/go-auth.md).

| | |
| --- | --- |
| Language | Go (standard library, `pgx`, `golang-jwt`, `rs/cors`, `google/uuid`) |
| Port | 8101 |
| Data | PostgreSQL only. The same database and `database_setup_history` table as the Rust service |
| Accounts | Firebase holds accounts and passwords (always needs `AUTH_FIREBASE_API_KEY`); this service keeps no passwords |
| Human check | Not here. The gateway checks reCAPTCHA; `AUTH_BOT_PROTECTION=true` stops this service from starting |
| Settings | The Rust service's names: [env/auth.production.example](../../env/auth.production.example) |

## What is built

Phase 1 of 5 (see the plan): `GET /healthz /version /.well-known/jwks.json /v1/security`, `POST /v1/accounts`, `POST /v1/sessions`, `POST /v1/sessions/refresh`, `POST /v1/sessions/sign-out`, `GET /v1/sessions`, `POST /v1/sessions/revoke`, `GET /v1/me`.

Not built yet, so the gateway must not send these here: password change, forgot and reset, email verify and resend (phase 2); every `/v1/mfa/*` route (phase 3); `/v1/providers`, `/v1/oauth/*`, `/v1/handoffs` (phase 4). A person who has a second step is answered `503 second_step_unavailable` and never gets a session: the service refuses rather than skips it.

## Same as the Rust service

Routes, JSON, error codes and sentences, the access token (EdDSA, issuer `callerwhale-auth`, audience `callerwhale`, claims `sub email name sid mfa email_verified provider auth_time iss aud iat exp`, key id from the public key), the lockout (five failed sign-ins for one email in 15 minutes), refresh-token rotation with theft detection, the signing key (`AUTH_SIGNING_KEY`, so tokens from either service verify with either's keys). A token signed here was checked against the Rust verifier (`callerwhale-auth-verify`) that the core API uses.

## Different on purpose

- A refresh is one conditional `UPDATE`: of two requests with the same token exactly one wins, the other looks like a copied token and ends the session.
- The schema loader holds a database lock, so several instances starting together do not race.
- A stop signal finishes the requests in flight, then closes (20 seconds at most).
- Anything that is not one of our own refusals is logged and answered as "Something went wrong."; request bodies, headers and tokens are never logged.

## Run and test

```bash
cd services/auth-go
go vet ./... && go test ./...        # PostgreSQL tests are skipped without AUTH_TEST_DATABASE_URL
AUTH_TEST_DATABASE_URL=postgres://postgres@127.0.0.1:5433/postgres go test ./...   # each test gets its own schema
DATABASE_URL=postgres://... AUTH_FIREBASE_API_KEY=... go run .
go run . new-key                      # prints a value for AUTH_SIGNING_KEY
```

`go run . health` is the container's health check (the image has no shell). The Firebase Auth Emulator can stand in for Firebase in development: set `AUTH_FIREBASE_IDENTITY_URL` and `AUTH_FIREBASE_TOKEN_URL` to it.

Build the image with this folder as the context: `docker build -t callerwhale-auth-go services/auth-go`. Logs follow `Design notes/Runtime logs.md` (the shared runner and `access_log.go`, both generated by `tools/runtime-log/sync.mjs`).

## Keep in step with the Rust service

Until the Rust service is deleted: a new numbered SQL file goes in both `database_setup` folders, and a route added to one goes in the other and in the gateway's allow-list (`services/gateway/shield.go`; its test compares that list with the Rust source).
