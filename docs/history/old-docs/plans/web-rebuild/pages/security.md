# Public security

Status: Proposed; planning only. Parent: [Web rebuild plan](../README.md).
Route/state: /security.

## Job

Describe actual protection and data handling so buyers can make an informed decision.

## Section plan

1. Security overview in plain language.
2. Central identity, account access and second-step options.
3. Data location, transport, retention and deletion facts with verified scope.
4. Public security contact and reporting route.
5. Known limitations and policy links.

## Actions and behavior

Primary: contact security/support. Link to Privacy; do not expose staff tools or internal system addresses.

## Layout and design

Use short factual sections and a readable policy layout. Keep claims distinct from planned safeguards.
Apply [shared experience rules](../01-experience.md), including light/dark, keyboard access and responsive review.

## Discovery and data protection

Public/indexable and sitemap. Never list admin/monitoring URLs in public search content.
Apply [discovery](../02-discovery.md) and [security](../03-security.md) contracts.

## Page acceptance

Security statements trace to current controls and configured behavior. No unsupported certification, encryption-at-rest or uptime promises. A report route has a real accountable recipient.
Record desktop/mobile light/dark evidence and loading, empty, success and failure states as applicable. Mark unsupported states explicitly rather than silently omit them.

## Detailed implementation brief

### Layout and sequence

Overview -> identity/session controls -> access/role boundaries -> data/desktop behavior -> retention/deletion facts -> report/contact -> policy links. Link the actual supported reporting channel, not staff tools.

### Copy and visual application

Headline proposal: 'Clear about your data and access.' Use evidence-led wording, minimal architectural decoration and readable paragraphs.

### Data and service boundary

Auth/core/notification/data owners confirm each statement. A security feature existing in source is not proof of production configuration. Keep exact internal topology and admin routes out of public copy.

### Required edge states

Unavailable reporting form/channel, unsupported assurances and policy changes have assigned owners; do not fill gaps with generic claims. Never publish an unverified compliance badge.

### Traceability

V01–V06, V28, V30. See [verification matrix](../12-verification-matrix.md), [contracts](../06-architecture-contracts.md) and [component/state rules](../09-components-interactions.md). Acceptance requires implementation evidence; this brief does not claim those integrations already work.
