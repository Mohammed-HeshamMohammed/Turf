# Terms

Status: Proposed; planning only. Parent: [Web rebuild plan](../README.md).
Route/state: /terms.

## Job

State supported service terms and access conditions accurately.

## Section plan

1. Responsible business, date and scope.
2. Invitation/access model and acceptable use.
3. Features, availability and limitations.
4. Pricing/billing/cancellation only where actually offered.
5. Suspension, responsibility, dispute/contact and revisions.

## Actions and behavior

Link to relevant policies; capture acceptance/version only when legally and operationally required by the approved signup design.

## Layout and design

Match Privacy's reading layout. No marketing signup overlay while reading.
Apply [shared experience rules](../01-experience.md), including light/dark, keyboard access and responsive review.

## Discovery and data protection

Public/indexable; sitemap once approved/current. Document legal review status in the plan, not misleading production copy.
Apply [discovery](../02-discovery.md) and [security](../03-security.md) contracts.

## Page acceptance

Obtain owner/legal approval before declaring terms final. Cross-check live sale/access rules; document how material updates are communicated.
Record desktop/mobile light/dark evidence and loading, empty, success and failure states as applicable. Mark unsupported states explicitly rather than silently omit them.

## Detailed implementation brief

### Layout and sequence

Business/date/scope -> product access/readiness -> acceptable use -> commercial terms only if applicable -> suspension/responsibilities -> contact/disputes -> changes. Reading page shares the visual system without oversized architecture.

### Copy and visual application

Describe invitation access and draft pricing accurately. Avoid free-trial/purchase/refund wording not supported by the approved offer.

### Data and service boundary

Business/legal owner approves the text; engineering documents what version/acceptance can actually be recorded. An arbitrary 'by continuing' sentence is not a substitute for a reviewed acceptance model.

### Required edge states

Old policy links, accessibility/print, policy revision and not-yet-approved commercial rules must be handled deliberately. Preserve accepted version history if collected.

V01–V06, V28, V30. See [verification matrix](../12-verification-matrix.md), [contracts](../06-architecture-contracts.md) and [component/state rules](../09-components-interactions.md). Acceptance requires implementation evidence; this brief does not claim those integrations already work.
